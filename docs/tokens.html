The tokens, one by one

Every payload here is real, captured on 2026-10-29 from a running petstore-auth; the tokens have expired and the key that signed them is gone. "Subject", "actor" and "issued" are the RFC 8693 names for the roles in a token exchange. All three are ordinary access tokens.

Who sends which token where

Solid arrows carry a token to the server that uses it. Dashed arrows are requests to petstore-auth's token endpoint, the only place tokens are made. The actor token and the refresh token never reach a resource server.

When each token is created

The gateway exchanges as the request arrives, before the MCP response starts (ApiTokenExchangeFilter), so a refused exchange is a plain 401. Cached tokens are renewed 30 seconds before they expire.

How long each token lives

At 5:00 mcp-remote trades the refresh token for a new pair; the old refresh token stops working. The new subject token isn't in the gateway's cache, so the gateway exchanges again and gets a new issued token.

Why each one is needed

subject

The gateway must know who is calling and what they approved, without ever seeing the password. Its aud makes it useless anywhere but the gateway.

refresh

Access tokens last 5 minutes to limit the damage of a leak. Without a refresh token the user would log in every 5 minutes. It rotates: each use retires it, so a stolen copy can't be used quietly alongside the real one.

actor

Says who is acting for the user; its sub becomes act. Without it the exchange would be impersonation: the new token would look like user1's own. TokenExchangeRules refuses that.

issued

The API accepts only tokens meant for it. Forwarding the user's token (token passthrough) is forbidden by the MCP spec; the gateway's own token has no user in it.

Scope: what it means, and where

A scope is a label. It means something only because a server compares it with a rule. Spring turns each one into an authority named SCOPE_<scope>, and the rules check those.

ServerWherepetstore.readpetstore.buy
GatewayMcpSecurityConfig, BuyStepUpFilterevery /mcp requesta tools/call of buyPet
APIApiSecurityConfigevery GET under /v2place an order, form update of a pet, delete an order
  • Same scope in the subject and issued tokens, because it records what the user approved, and that doesn't change when the token moves to another server. RFC 8693 would allow fewer (down-scoping), never more.
  • It comes from petstore-auth's record of the login, not from reading the subject token. When that record is gone (a restart, a revoked login) the exchange fails, even if the subject token still looks valid.
  • The consent page shows the raw names as checkboxes, with no description, and names the app by its client ID, petstore-mcp-client.
  • A label can promise less than the rule allows. petstore.buy sounds like "buy a pet", but at the API it also allows renaming any pet and changing its status, because buyPet is built from three general-purpose calls. (Cancelling is limited to the user's own orders, since step 7.)

Step-up changes only the scope: after user1 approves buying, the new subject token has ["petstore.read", "petstore.buy"]. It isn't in the gateway's cache, so the gateway exchanges it, and the new issued token carries both scopes too.

How a JWT is checked

The gateway and the API check tokens the same way, locally, without asking petstore-auth about each one:

  1. Read kid and find that key in GET http://localhost:9000/oauth2/jwks (the gateway fetches it on the first token and caches it for 5 minutes).
  2. Check the signature. A changed claim, or a token signed by anyone else, fails here.
  3. iss must be http://localhost:9000.
  4. exp and nbf must allow now.
  5. aud must contain this server's own URL.
  6. The request must be allowed by the token's scopes.
{ "keys": [ { "kty": "RSA", "e": "AQAB", "kid": "e3b8e77b-3283-4b42-8cd9-3113a53bce6a", "n": "9NqCPC8c6UC6…" } ] }

Only the public half is published. The key pair is created at startup and kept in memory, so restarting petstore-auth makes every existing token fail step 1.

Rules of thumb

One token, one server

aud decides where a token works. Every hop to a new server gets a new token.

Never forward the user's token

The gateway exchanges it; it doesn't pass it through.

User in sub, program in act

The API knows both who is asking and what is asking for them.

Scope never grows on the way

More permission means asking the user again (step-up).

Short-lived, rotating

A leaked access token expires in minutes. A leaked refresh token can't be shared quietly, because each use retires it.
