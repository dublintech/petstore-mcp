# The OAuth flow, request by request

What happens from the moment Claude Desktop starts `mcp-remote` to the first tool call, in a fresh run (nothing saved
in `~/.mcp-auth`, gateway just started). The same diagram as a coloured web page is in
[`oauth-flow.html`](oauth-flow.html); download it and open it in a browser.

## Key

**Where a value is defined**

| Marker | Defined in |
|---|---|
| 🔵 | Claude Desktop config (`claude_desktop_config.json`) |
| 🟣 | Server config (`application.properties` of petstore-auth or the gateway) |
| 🟠 | Generated by `mcp-remote` at runtime |
| 🟢 | Issued by a server at runtime |
| 🟡 | Typed or chosen by the user |
| ⚪ | Fixed by the OAuth or MCP spec |

**Privacy:** 🔒 marks a secret. Anything without it is public.

**Channels:** the orange band is the **front channel**, the steps that go through the browser. Its URLs end up in
browser history, logs and `Referer` headers, so nothing there may be secret except the one-time code. The blue band is
the **back channel**: direct requests between programs, where the secrets travel in bodies and headers.

## The flow

```mermaid
sequenceDiagram
    autonumber
    participant D as Claude Desktop
    participant R as mcp-remote<br/>127.0.0.1:3334
    participant B as Browser
    participant A as petstore-auth<br/>localhost:9000
    participant G as Gateway<br/>localhost:8081
    participant P as petstore-api<br/>localhost:8080

    D->>R: starts npx -y mcp-remote@0.15.0
    Note right of D: 🔵 http://localhost:8081/mcp<br/>🔵 3334<br/>🔵 client_id petstore-mcp-client<br/>🔵 --auth-timeout 120

    rect rgba(128, 128, 128, 0.10)
    Note over R,G: Discovery: public metadata, no token needed
    R->>G: GET /mcp (no Authorization header)
    G-->>R: 401 WWW-Authenticate: Bearer resource_metadata=.../.well-known/oauth-protected-resource
    R->>G: GET /.well-known/oauth-protected-resource
    G-->>R: 200 🟣 resource, 🟣 authorization_servers, 🟣 scopes_supported
    R->>A: GET /.well-known/oauth-authorization-server
    A-->>R: 200 🟣 authorize, token and jwks URLs, 🟣 S256 supported
    Note over R: saves in ~/.mcp-auth:<br/>🟠🔒 code_verifier<br/>🟠 code_challenge = BASE64URL(SHA256(verifier))<br/>🟠 state
    end

    rect rgba(255, 165, 0, 0.16)
    Note over R,A: Front channel: through the browser
    R->>B: opens the browser on the authorize URL
    B->>A: GET /oauth2/authorize
    Note over B,A: ⚪ response_type=code, 🔵 client_id, 🔵 redirect_uri=http://127.0.0.1:3334/oauth/callback<br/>🟠 code_challenge, ⚪ code_challenge_method=S256, 🟠 state<br/>🟣 scope=petstore.read petstore.buy, 🟣 resource=http://localhost:8081/mcp
    Note over A: checks client_id and redirect_uri against the registration,<br/>saves the request in the session
    A-->>B: 302 to /login, 🟢🔒 JSESSIONID cookie
    B->>A: POST /login: 🟡 username, 🟡🔒 password, 🟢 _csrf
    A-->>B: 302 to the saved authorize URL + &continue, 🟢🔒 new JSESSIONID
    B->>A: GET authorize again, consent page, POST consent with 🟡 approved scopes
    A-->>B: 302 to 127.0.0.1:3334/oauth/callback with 🟢🔒 code and 🟠 state
    B->>R: GET /oauth/callback?code&state
    Note over R: checks state is a login it started,<br/>loads that login's verifier
    end

    rect rgba(70, 130, 230, 0.14)
    Note over R,G: Back channel: direct requests
    R->>A: POST /oauth2/token (form body): 🟢🔒 code, 🟠🔒 code_verifier, 🔵 redirect_uri, 🔵 client_id, 🟣 resource
    Note over A: checks SHA256(verifier) = saved challenge.<br/>No client secret: public client.
    A-->>R: 200 🟢🔒 access_token (JWT, 5 min), 🟢🔒 refresh_token (8 h, rotates)
    R->>G: POST /mcp initialize, Authorization: Bearer 🔒
    G->>A: GET /.well-known/openid-configuration + /oauth2/jwks (first token only, cached 5 min)
    A-->>G: 200 🟢 public key. The private key never leaves petstore-auth.
    Note over G: checks locally: signature, exp,<br/>🟣 iss, 🟣 aud, 🟣 scope petstore.read
    G->>A: POST /oauth2/token: ⚪ grant_type=client_credentials, 🔒 gateway secret (Basic auth). First time only.
    A-->>G: 200 🟢🔒 the gateway's own token (sub = aud = petstore-gateway)
    G->>A: POST /oauth2/token: ⚪ grant_type=token-exchange, 🔒 subject_token (the user's), 🔒 actor_token (the gateway's), 🟣 resource=http://localhost:8080
    Note over A: checks the gateway's secret, that the user's token is meant for the gateway,<br/>and no more scope than the user approved
    A-->>G: 200 🟢🔒 API token: sub=user1, aud=http://localhost:8080, the user's scopes, act=petstore-gateway
    Note over G: cached per user token until it expires
    G-->>R: 200 capabilities, 🟢 Mcp-Session-Id
    end

    rect rgba(128, 128, 128, 0.10)
    Note over R,P: Using the tools
    R->>G: POST /mcp tools/call findPetsByStatus, Bearer 🔒, Mcp-Session-Id
    G->>P: GET /v2/pet/findByStatus?status=available, Bearer 🔒 API token
    Note over P: checks 🟣 aud = http://localhost:8080 and 🟣 scope petstore.read
    P-->>G: 200 pets
    G-->>R: 200 result
    loop every ~5 minutes
        R->>A: POST /oauth2/token: ⚪ grant_type=refresh_token, 🟢🔒 refresh_token, 🔵 client_id
        A-->>R: 200 🟢🔒 new access_token, 🟢🔒 new refresh_token (the old one stops working)
    end
    end
```

Step 15, the callback to `127.0.0.1:3334`, isn't visible in mitmweb; only the 302 that causes it is.

## Which server is the token for?

The token names two servers, in two claims:

| Claim | Value | Means |
|---|---|---|
| `iss` | `http://localhost:9000` | Issued by one authorization server, petstore-auth |
| `aud` | `http://localhost:8081/mcp` | Accepted by one resource server, the gateway. Any other service should refuse it. |

The API token from the exchange has the same `iss` but `aud` = `http://localhost:8080`: only the API accepts it.

## Who holds what

● holds it · 🔒 holds it and it's secret · ○ holds only the public half or a hash

| Value | Kind | mcp-remote | Browser | petstore-auth | Gateway | Why it's safe |
|---|---|:-:|:-:|:-:|:-:|---|
| `client_id` | public | ● | ● | ● | | Names the app, not the user |
| `state` | public | ● | ● | ● | | Lets `mcp-remote` reject callbacks it didn't start |
| `code_challenge` | public | ● | ● | ● | | A hash: the verifier can't be worked out from it |
| `code_verifier` | secret | 🔒 | | 🔒 | | Back channel only, used once, then deleted |
| password | secret | | 🔒 | ○ | | Typed only into petstore-auth's own page |
| `JSESSIONID` | secret | | 🔒 | 🔒 | | HttpOnly cookie, renewed at login |
| authorization code | short-lived secret | 🔒 | 🔒 | 🔒 | | Useless without the verifier, single use, 5 minutes |
| access token | secret | 🔒 | | 🔒 | 🔒 | Lasts 5 minutes; `aud` limits it to the gateway |
| refresh token | secret | 🔒 | | 🔒 | | Never sent to the gateway; rotates on every use |
| API token | secret | | | 🔒 | 🔒 | Lasts 5 minutes; also held by the API. Its `aud` is the API, so the gateway can't use it on itself |
| gateway client secret | secret | | | ○ | 🔒 | petstore-auth keeps only a BCrypt hash |
| signing key | secret | | | 🔒 | ○ | The gateway and the API hold only the public half (JWKS) |

## Rules of thumb

- **Front channel: nothing secret.** The only sensitive value is the code, and it's useless without the verifier.
- **Back channel: the secrets.** The verifier and the tokens travel only in direct requests. In production these use
  HTTPS; mitmweb sees them only because it sits in the middle on plain http.
- **The private key never moves.** petstore-auth signs with it; the gateway checks every token locally with the
  public key, without calling back.
